5Multi-agent and product patterns

Once one agent loop works, the questions become structural: how to split work, how to survive long runs, where people should step in, and when to skip the agent altogether.

5.1Orchestrator and workers

One agent plans and delegates, workers run in fresh contexts, and everything crosses the boundary as a written brief and a written summary, which is both the benefit and the cost.

An orchestrator is an agent whose main tool is "start another agent". It writes a brief, a worker (often called a subagent) runs its own loop in a clean context window, and only the worker's final message comes back. The worker's file reads, dead ends and long tool outputs never enter the orchestrator's context.

          orchestrator
         /     |      \
     brief   brief   brief
       |       |       |
    worker  worker  worker
       |       |       |
    summary summary summary
         \     |      /
          merge + check

Three common shapes:

  • Pipeline. Stages in sequence: research, then plan, then implement, then test. Each stage gets a clean context and a focused prompt.
  • Fan-out and merge. Split independent work (one worker per module, per file, per question) and run in parallel. The orchestrator merges and resolves conflicts.
  • Parallel review. Several reviewers look at the same change through different lenses (correctness, security, performance). A final step deduplicates findings and ideally verifies each one, because reviewers produce plausible false positives.

Now the honest part: the handoff tax. The worker knows only what the brief says. Anything the orchestrator learned and did not write down is lost, so thin briefs produce workers that redo exploration or make wrong assumptions. In the other direction, the summary is lossy compression. The orchestrator cannot see what the worker skipped, misread or quietly gave up on, and a confident summary reads the same as a correct one.

Costs multiply too. Each worker rereads files and rebuilds context, so total tokens can be several times a single-agent run. Parallelism pays when the subtasks are genuinely independent, each needs a lot of reading, and the results are easy to check. It hurts when workers need each other's decisions, or when merging is harder than doing the work.

Practical habits: put file paths, constraints and the definition of done in the brief; ask workers for evidence (paths, line numbers, command output) rather than conclusions; and spot-check before trusting a merged result.

When a Claude Code subagent returns a tidy paragraph and the main session then rereads the same files, that is the handoff tax: the summary was not enough to act on. A more specific brief or a request for exact paths often fixes it.

Subagents buy clean context and parallelism at the price of lossy briefs and summaries. Split only where the pieces are independent and the results are checkable.

5.2Long-running agents

A long task outlives any one context window or process, so the agent's real memory has to live on disk: progress files, commits and checkable state.

Agents running for hours hit three walls. The context window fills and gets compacted (summarized, see 4.3), losing detail. The process stops: a crash, a closed laptop, a rate or usage limit. And small errors compound over many steps. Each wall has the same answer: do not keep important state only in the conversation.

Patterns that work:

  • A progress file. A plain markdown or JSON file listing the plan, what is done, what is next and any decisions made. The agent updates it after each step and reads it first on resume. It is short, so it survives compaction cheaply.
  • Git as checkpoints. Commit after each verified step. Commits are durable, diffable and easy to roll back, and the log doubles as a history the next session can read.
  • Small, idempotent steps. Design each step so running it twice is safe (check whether the output exists before creating it). Then "resume" can simply mean "rerun from the last unfinished item".
  • Verify on resume. A fresh session should check reality (run the tests, list the files) instead of trusting the notes. Notes can claim work that was never finished.
  • External ground truth. A test suite or checklist that defines done lets any session, including a brand new one, tell where things stand.

Most harnesses can also resume a saved conversation. That helps, but a resumed transcript is a large, partly stale context. A fresh session that reads a good progress file is often sharper than an old one dragged back to life.

For production systems, the same idea is called durable execution: workflow engines record each step's result so a restarted job continues where it stopped instead of starting over. If you build agent features at work, treat each model call and tool call as a step that might need replaying.

If you have hit a usage limit halfway through a refactor, or watched a session compact and then forget a decision you made an hour earlier, you have seen why state in the chat is fragile. Asking the agent to keep a progress file and commit as it goes turns those events into a short pause.

Treat the context window as scratch space. Plans, progress and decisions go in files and commits, and every resume starts by checking reality.

5.3Human in the loop

Put approval at the points where a mistake is expensive or cannot be undone, not on every step, or people stop reading what they approve.

Approval has a cost that is easy to miss: attention. If an agent asks permission for every file read, you will click yes reflexively within minutes, and the one prompt that mattered gets the same reflex. This is approval fatigue, and it turns a safety mechanism into a ritual.

A useful way to decide where humans belong is to sort actions by reversibility and blast radius:

ActionExampleCheck
Read-onlyread, grep, listnone
Local, reversibleedit files under gitreview the diff
Shared or externalpush, send, deployapprove each
Destructivedelete data, payapprove, or forbid

Patterns that protect without stalling:

  • Approve plans, not keystrokes. Review the approach once up front, then let the agent execute. A bad plan is cheap to reject; a bad plan half implemented is not.
  • Review outcomes at the end. For local work under version control, one review of the final diff is usually worth more than twenty approvals of individual edits.
  • Batch questions. An agent that collects its open questions and asks them together costs you one interruption, not five.
  • Keep working while waiting. In async setups, the agent can continue on reversible work and park only the step that needs a decision.
  • Enforce, do not only ask. A sandbox or deny rule stops an action even if you approve carelessly; a prompt saying "ask before deleting" only asks the model to remember (see 4.5).

When you design an AI feature for other people, the same rule applies: make the confirmation show exactly what will happen (the recipient, the amount, the rows affected) so the human is checking facts rather than trusting a summary.

Claude Code's permission prompts, allow rules and plan-first workflows are this trade-off made concrete. Allowing safe commands broadly and keeping prompts for pushes and deletes is what keeps the remaining prompts worth reading.

Spend human attention where mistakes are irreversible or leave your machine. Everywhere else, use version control and a final review instead of step-by-step approval.

5.4When not to use an agent

If you can write the steps down in advance, write code; reach for a model only where judgment is needed, and for an agent only where the path is unknown.

An agent is a model choosing its next step in a loop. That flexibility is useful when the path is unknown and expensive when it is not: you pay in latency, tokens, run-to-run variation and harder debugging. A useful ladder, from cheapest to most flexible:

  1. Plain code. Deterministic, fast, testable, free to run.
  2. One model call. Classify, extract, summarize or rewrite a single input. No loop.
  3. A fixed workflow. Several model calls wired together by your code in a set order, maybe with a branch. You own the control flow.
  4. An agent. The model owns the control flow and decides which tools to call and when to stop.

Climb only as far as the task forces you. Concrete signs that plain code wins:

  • You could draw the process as a flowchart before seeing the input.
  • The correct output is defined by a rule (a format conversion, a migration, a lint fix with a known pattern).
  • It runs often, at volume, or under a latency budget.
  • You need identical results every time, or an audit trail a reviewer can follow.
  • A wrong answer is costly and hard to detect.

Signs a single call or fixed workflow is enough: the input is self-contained, the steps are known, and only one step needs judgment (reading messy text, choosing a category). Keep the model in that one step and let code do the rest.

Signs an agent earns its cost: you cannot know in advance which files, pages or commands matter; the task needs exploring, trying and checking; and the result can be verified (tests pass, the page renders). Debugging an unfamiliar codebase is the classic case.

The best move is often a mix: use the agent to write the code. Ask it to explore once and produce a script, review the script, then run the script a thousand times. You get the agent's flexibility once and code's reliability forever.

Agents are for unknown paths. Known paths belong in code, and judgment on a single input belongs in a single call.
