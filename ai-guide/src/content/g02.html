2Prompting and context engineering

The model knows only its context window. What goes in, in what order, and what stays stable between calls decides quality, speed and cost, in a chat or inside an agent.

2.1System prompts and the instruction hierarchy

Models are trained to weight the system prompt above the user, and the user above documents and tool results, but that ranking is a learned tendency, not an enforced rule.

A chat API request has three kinds of content. The system prompt sets role, rules and background for the whole conversation. Then come alternating user and assistant turns; in Anthropic's Messages API, tool results come back inside user turns (see 3.1).

Underneath, it is all one token sequence with special tokens marking where each role starts, and nothing in the architecture makes the system prompt special. Training does: the model learns an instruction hierarchy, roughly system over user over third-party content. Fetched web pages, file contents and tool output are meant to be treated as data, not commands.

Because the hierarchy is learned, it is a strong tendency with exceptions. A well-crafted instruction hidden in a web page can still be followed, which is the whole problem of prompt injection (see 10.1). Anything that must hold no matter what belongs in code outside the model: permission checks, sandboxes, validation (see 4.5).

What belongs in a system prompt:

  • Who the model is serving and what the job is.
  • Stable rules and constraints, each with its reason.
  • How to use the tools, and when not to.
  • Output format, ideally with a short example.

Some habits work better with current models. Explain why a rule exists, since a reason generalizes to cases the rule did not name. Skip the shouting: capitals and repeated "MUST" helped older models but tend to cause overcorrection in newer ones.

Say what to do rather than only what not to do. Keep examples varied, because the model copies them closely, including their quirks.

CLAUDE.md and similar instruction files are injected into the context by the harness, early in the conversation. That is why they are followed by default, why a direct request later in the session can override them, and why rules can seem to fade once a long session buries them under newer tokens.

The hierarchy shapes behavior; it does not enforce it. Put preferences in prompts and guarantees in code.

2.2Context engineering: what to include and in what order

Give the model everything the task needs and nothing it does not, with stable material first and the actual request last.

Context engineering is the broader form of prompt writing: deciding everything that enters the window, including system prompt, tool definitions, instruction files, retrieved documents, history and tool results. The model knows nothing outside it, so a missing fact becomes a guess (see 1.4).

More is not better. Irrelevant text costs tokens, slows every call, and competes for attention with what matters; quality on many tasks drops as context grows, an effect often called context rot. Aim for the smallest set of high-signal tokens that makes the right answer likely.

A practical order, top to bottom:

  1. Stable instructions: role, rules, tool definitions. They rarely change, so they cache well (see 2.3).
  2. Reference material: docs, specs, relevant files, each wrapped in clear delimiters such as XML-style tags naming the source.
  3. History: prior turns and tool results, trimmed or summarized when stale.
  4. The request: the specific task, last. With long documents, a question placed after them tends to get better answers than one placed before.

In the request itself, include what a capable new teammate would need: the goal and why it matters, constraints, what "done" looks like and how to check it. If format matters, show an example. Name things precisely: a file path or function name beats "the auth code".

For agents, prefer just-in-time context. Give the model tools to fetch what it needs (search, read a file, list a directory) instead of preloading everything, so it pulls in the three relevant files rather than carrying the whole repo (see 7.3).

Watching Claude Code grep and read a few files before editing is this principle at work. When a long session is compacted, the harness is doing context engineering for you: replacing a pile of old tool output with a summary so the window holds signal again (see 4.3).

Every token should earn its place. Stable first, request last, references clearly labeled.

2.3Prompt caching

Providers can skip reprocessing a prompt prefix they have seen recently, which makes repeated calls much cheaper and faster, but only if that prefix is exactly identical.

When a model reads your prompt, each layer computes keys and values for every token (the KV cache, see 9.1). Because attention only looks backward, a token's keys and values depend only on the tokens before it. So if a new request starts with exactly the same tokens as an earlier one, that work can be reused.

Prompt caching stores those computed states for a prefix and reuses them on a match. The rules follow from the mechanism:

  • Prefix only. Matching runs from the first token forward and stops at the first difference. Everything after a change is recomputed, even if it is identical.
  • Exact. One changed character, a reordered tool list or a timestamp in the system prompt breaks the match from that point on.
  • Per model. Cached states belong to one model; switching models starts cold.
  • Short-lived. Entries expire after a few minutes unused, with longer-lived options on some providers; each hit refreshes the timer.

Some providers cache automatically; Anthropic's API lets you mark cache breakpoints explicitly. Either way, cached input is billed at a fraction of the normal input price, writing to the cache can cost a little more, and time to first token drops.

turn 9:  [tools][system][m1 .. m8]
turn 10: [tools][system][m1 .. m8][m9]
         \_______ cache hit ______/ new

system prompt edited mid-session:
         [tools][SYSTEM*][m1 .. m9]
         \hit_/ \__ all recomputed __/

This is why order matters (see 2.2): stable parts first, conversation append-only. An agent loop suits caching well, since each turn resends the previous prompt plus a little more.

Come back to a Claude Code session after a long break and the first reply can be slower and cost more of your limit, because the cache expired. Switching models, changing the set of available tools, or compacting history also invalidates large parts of the prefix.

Stable first, append only, nothing volatile near the top. A cache hit makes a long context cheap; a miss makes you pay for all of it again.

2.4Decomposition and chain of thought

Hard tasks go better broken into steps, either inside one response (reasoning before answering) or across several calls with checks in between.

Chain of thought means having the model reason through intermediate steps before committing to an answer. It works for the mechanical reason in 1.3: each written step becomes context later tokens can use, which gives more computation per problem. With reasoning models that think by default, "think step by step" adds less; a clear goal and room to think matter more.

Decomposition moves the steps out of one response and into separate stages. Common shapes:

  • Plan, then execute: one pass writes a plan you can review; later passes carry it out.
  • Prompt chaining: the output of one step (extract the API surface) becomes the input of the next (write the migration).
  • Generate, then verify: a separate call, ideally with fresh context, checks the result against the requirements or runs the tests.
  • Fan-out: independent parts processed in parallel, then merged (see 5.1).

Splitting helps because each stage gets a focused context with only what it needs. You can inspect and correct between stages instead of finding a bad assumption at the end, and cheap stages can run on a smaller model. A verifier that did not write the code is also less likely to share the author's blind spots.

Splitting hurts because every handoff compresses information, and the next stage cannot ask what the previous one meant. More stages also mean more latency and more total tokens. If a task is small enough for one strong model to hold all of it, one call is usually better.

A useful test: split where you would want to review the work anyway, or where the steps genuinely need different context. Do not split just because the task is long.

Plan mode, to-do lists and subagents in Claude Code are decomposition built into the harness. A subagent's summary is a handoff: focused and cheap for the main context, but anything it left out is gone (see 4.6).

Split where review points or context boundaries fall naturally. Each split buys focus and a checkpoint, and costs a lossy handoff.

2.5Long context versus retrieval

You can put everything in the window and let attention find what matters, or select the relevant pieces first; each fails differently, and good systems usually combine them.

Context windows now hold hundreds of thousands of tokens, enough for a sizable codebase or a stack of documents. That raises a design question: load it all, or retrieve only the relevant parts?

Long context is simple and sees everything at once. The model can connect a detail in one file to a detail in another without anyone predicting that link in advance. The costs: every call pays for every token (caching softens this, see 2.3), time to first token grows, and quality degrades with length, especially when many scattered facts must be combined rather than one fact found.

Retrieval picks a small set of pieces first, using keyword search, embedding similarity (see 7.1) or an agent searching with tools. It scales to any corpus size, stays current as files change, and keeps each call small. Its failure is silent: if the retriever misses the relevant piece, the model answers confidently from what it was given (see 1.4).

Rules of thumb:

  • Small, stable corpus queried many times: put it in context and cache it.
  • Large or fast-changing corpus: retrieve.
  • Often best: retrieve to find the relevant files, then load those files whole rather than as fragments.

Coding agents mostly take the agentic route: grep, glob and read on demand, then keep the important files in context. Exact-match search works well on code because identifiers are precise (see 7.3).

Long Claude Code sessions lose sharpness partly for the long-context reason: old file reads and tool output dilute attention even though they still fit. Starting a fresh session with a short handoff note often beats pushing on in a full window.

Fitting in the window is not the same as being used well. Retrieve to narrow, then give the model whole, relevant pieces.
