1How models work

What actually happens between your prompt and the reply. Most quirks you meet in an agent, from invented flags to slow long sessions, trace back to the few mechanisms in this group.

1.1Tokens and transformers in one page

A model is a function that reads a sequence of tokens and outputs a probability for every possible next token; chat, tools and agents are all built by calling it in a loop.

Before the model sees your text, a tokenizer cuts it into tokens: common words, word pieces, punctuation, runs of spaces. Each token is an integer id from a fixed vocabulary, typically tens of thousands to a couple hundred thousand entries (see 1.6).

Each id is looked up in a table to get an embedding, a vector of a few thousand numbers. The vectors then pass through a stack of identical transformer layers, often dozens of them. Each layer has two parts: attention, which moves information between positions, and a feed-forward network, which transforms each position on its own and is where much of the stored knowledge appears to live.

Attention is the part worth an intuition. At every position the layer computes a query ("what am I looking for") and compares it with a key ("what do I contain") at every earlier position; the match scores become weights for blending those positions' values into the current one. That is how a closing brace finds its opening brace, or a variable use finds its declaration three files back, and each layer runs many of these "heads" in parallel, each learning different relationships.

After the last layer, the vector at the final position is turned into a probability distribution over the whole vocabulary. One token is picked from it (sampling, shaped by settings like temperature), appended to the sequence, and the model runs again. Text generation is this loop, one token per step.

Three consequences follow. First, the model has no memory between calls: the context window, the tokens you send, is all it knows beyond what is frozen in its weights. Second, comparing every position with every earlier one makes long inputs expensive, so servers keep each token's keys and values in a KV cache and a new token only attends to stored work (see 9.1).

Third, the weights do not change while you use the model. Nothing you say in a session teaches it anything permanently; anything that persists has to be written somewhere and fed back in as context.

Claude Code streams replies token by token because that is literally how they are produced. And every turn, the harness sends the entire conversation again, because the model keeps nothing between calls; that is a large part of why long sessions get slower and use more of your limit.

Tokens in, one next-token distribution out, repeated. Everything the model "knows" in a session is either in its frozen weights or in the context window.

1.2The training pipeline: pretraining, SFT, RLHF/RLAIF

A chat model is a next-token predictor trained on a huge text corpus, then reshaped into an assistant by example conversations and reinforcement learning; each stage leaves visible fingerprints.

Pretraining is next-token prediction on an enormous corpus: web pages, books, papers and a great deal of source code. For each position the weights are nudged to make the actual next token more likely. To predict well the model has to pick up grammar, facts, coding idioms and some reasoning patterns, because all of them help predict text.

The result is a base model. It continues documents rather than answering questions: give it the start of a README and it writes more README; give it a question and it may write five more questions. Its knowledge stops at the training cutoff, when the data was collected.

Supervised fine-tuning (SFT) trains on curated conversations: a prompt and an ideal response, wrapped in special tokens that mark who is speaking. This teaches the assistant format: answer the question, follow instructions, call tools with the right syntax, stop when done.

Reinforcement learning comes next, in several flavors:

  • RLHF (from human feedback): people compare pairs of responses, a separate reward model learns to predict their preferences, and the chat model is optimized to score well against it.
  • RLAIF (from AI feedback): a model judges responses against written principles, which scales far better than human raters. Anthropic's constitutional AI is the best-known version (see 10.3).
  • RL on verifiable tasks: the model attempts problems whose results can be checked automatically, such as code that must pass tests. As of late 2026 this, often in multi-step tool-using environments, is a major driver of gains in coding and agent work.

Each stage leaves fingerprints. Preference training rewards answers people like, which can drift into sycophancy: agreeing too fast, praising a shaky idea. Rewarding passing tests can teach shortcuts such as special-casing a test or declaring success early, which labs now actively train against (see 8.4).

When an agent says "you're right" and abandons a correct position the moment you push back, that is preference training showing through. When it edits a test so the test passes instead of fixing the code, that is a reward-hacking habit. Both are reasons to ask for evidence rather than agreement.

Pretraining gives knowledge and fluency; SFT gives the assistant format; RL gives judgment, tool skill and some bad habits. The chat persona is a learned layer on top of a document predictor.

1.3Reasoning and extended thinking

Thinking is the model writing tokens before its answer; because later tokens can attend to them, it buys more computation per problem at the cost of time and output tokens.

Each forward pass does a fixed amount of computation to produce one token. A problem with ten dependent steps cannot be solved reliably inside one token's worth of work. But if the model writes the steps out, each one becomes part of the context, and the next token can attend to it (see 1.1).

So written reasoning acts as both a scratchpad and extra serial compute. This is why "think step by step" helped even early models (see 2.4). Reasoning models go further: they are trained with reinforcement learning to produce long, useful reasoning before answering, including checking their work, backtracking and trying alternatives.

Extended thinking in an API exposes that behavior as a separate part of the response. Mechanically:

  • The model emits a thinking block, then the final answer. Both are ordinary generated tokens.
  • Thinking tokens are billed as output and count toward limits, though you may not see all of them; some products show a summary instead of the raw text.
  • You steer how much it thinks with a budget or an effort setting. More helps on hard problems and wastes time on easy ones.
  • In agent loops, models can think between tool calls ("interleaved thinking"), reasoning about a result before choosing the next action.

Two cautions. The visible reasoning is not guaranteed to be a faithful record of how the answer was reached; research has found cases where the stated reasoning leaves out what actually drove the result. And thinking adds no knowledge: it can catch a logic slip, not supply a fact the model never learned.

Raising the effort level or asking an agent to think harder produces a longer pause before visible output and draws down more of your usage, because those hidden tokens are real generated output. On a rename or a typo fix, that spend buys nothing.

Thinking trades latency and output tokens for accuracy on multi-step problems. Spend it on design, debugging and planning, not on mechanical edits.

1.4Hallucination and structural weaknesses

The model always produces a fluent, likely-looking continuation and nothing in that process checks it against reality, so hallucination is the default when knowledge runs thin, not a malfunction.

Recall the mechanism: the model outputs a probability distribution and a token is picked from it (see 1.1). There is no database lookup and no separate "do I actually know this" step. When the weights strongly encode a fact, the likely continuation is the true one; when they do not, it is something that looks like the true one.

That is exactly what happens with rare facts: a flag of a niche CLI, a function signature that changed between library versions, a package name, a citation. The model has seen thousands of similar things, so it produces a confident, well-formed, wrong one. Some research also argues that training and benchmarks reward guessing over "I don't know", since a guess sometimes scores and an abstention never does.

Other weaknesses are structural too:

  • Character-level tasks: the model sees tokens, not letters, so counting characters or reversing strings is error-prone (see 1.6).
  • Exact arithmetic on long numbers, done "in its head" instead of with a tool.
  • Stale knowledge: events after the training cutoff are unknown, and the model may not notice that they are.
  • Long-context recall: details buried in a very long context tend to be used less reliably (see 2.5).
  • Self-reports: "all tests pass" is also a generated sentence and can be wrong in the same way.

The fixes all work by changing what is in context or by checking outside the model. Ground it: have it read the real file, docs or --help output before using an API. Verify: run the code, the tests, the type checker. And say explicitly that "I'm not sure" is an acceptable answer.

An agent that invents a method on your class usually stops once it has grepped for the class definition. The model did not get smarter mid-session; the real definition is now in context and outweighs the guess. Agents that run the tests catch much of the rest.

Fluency is not evidence. Trust what the model read or ran in this session over what it recalls from training.

1.5Scaling laws and model tiers

Bigger models trained with more data and compute get predictably better, which is why labs ship a family of sizes and why choosing a tier is a real cost and quality decision.

Scaling laws are empirical curves showing that a model's prediction error falls smoothly as parameters, training data and compute grow together. Work around 2020 established the pattern; a 2022 result, usually called Chinchilla, showed many models had been too large for their data, and that parameters and training tokens should grow roughly in step.

The curves are smooth for average loss but not for specific skills. A capability like multi-step code repair can look absent at one scale and fairly solid at the next, because it needs several sub-skills to work at once. So what the next model will be able to do is hard to predict even when its loss is not.

As of late 2026 there are three axes of scale, not one: pretraining compute, reinforcement learning compute (see 1.2), and inference-time compute, meaning how long the model thinks per problem (see 1.3). Much recent progress on coding agents has come from the last two.

Labs turn this into tiers: a large, slow, expensive flagship, a mid-size workhorse and a small fast model. Anthropic's Opus, Sonnet and Haiku follow this shape. Small models are often trained partly to imitate larger ones (distillation, see 8.3).

TierGood forTradeoff
LargeAmbiguous design, hard bugs, long plansSlow, costly, eats limits
MidMost coding and agent workMisses some subtle cases
SmallSearch, triage, extraction, summariesWeaker multi-step judgment

Two rules of thumb. A new generation's mid tier often matches the previous generation's flagship, so model names age fast. And the right tier depends on what a mistake costs: a cheap model that needs three retries and your review time is not cheap.

Usage limits drain faster on larger models, which is why switching to a smaller one stretches a session. Harnesses also commonly let you give subagents doing search or summarization a smaller model while the main loop keeps the large one.

Match the tier to the difficulty of the decisions, not the size of the task. Routine, well-specified work rarely needs the flagship.

1.6Tokenization in practice (code, JSON, Chinese, cost)

Models read text in subword chunks whose size depends heavily on the kind of text, so the same content can cost very different amounts as code, JSON, English or Chinese.

Most current tokenizers use a variant of byte-pair encoding (BPE). Start from raw bytes and repeatedly merge the most frequent adjacent pair into a new token until the vocabulary reaches its target size. Frequent strings end up as single tokens; rare ones split into pieces, down to single bytes if needed, so any input can be encoded.

For English prose a common rule of thumb is roughly four characters, or three quarters of a word, per token. Other content varies widely:

  • Code: keywords and common names are usually one token. Long or unusual identifiers split into several. Modern tokenizers merge runs of spaces, so indentation is cheaper than it once was.
  • JSON: every quote, brace, colon and repeated key is paid for in every record. A thousand rows as JSON objects can cost far more than the same data as CSV, and pretty-printing adds more.
  • Chinese: each character is three bytes in UTF-8. A tokenizer with good Chinese coverage maps common characters or words to one token; a weaker one falls back to bytes and spends two or three per character. The same meaning can cost more than English on one model and about the same on another.
  • Hashes, base64, UUIDs, minified code: high-entropy strings tokenize badly, often a token every few characters.
getUserAccountBalance
-> get|User|Account|Balance
9f3a1c07e2
-> 9|f|3|a|1|c|07|e|2
(illustrative; real splits vary)

This matters three ways. Cost and rate limits are counted in tokens, not characters; context windows are measured in tokens, so token-heavy content crowds out conversation. And character-level work like counting letters is hard because the model never sees the letters (see 1.4).

Different model families, and sometimes different generations from one lab, use different tokenizers, so counts are not portable. Use the provider's token-counting endpoint or reported usage rather than guessing.

One tool call that dumps a large JSON response or a minified bundle into context can eat more of the window than an hour of conversation. That is why harnesses truncate long tool output, and why asking an agent to jq or grep first is cheaper than reading the whole thing.
