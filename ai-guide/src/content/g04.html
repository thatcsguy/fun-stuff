4Agent harnesses: the loop around the model

Claude Code is a model plus a program that runs it in a loop. This group opens that program up: what it does between model calls, and why compaction, permission prompts, subagent summaries and usage limits behave the way they do.

4.1The core loop

An agent is a while-loop: call the model, run the tools it asked for, append the results, and call again until it stops asking.

The model is stateless. Each API call takes the whole conversation so far (system prompt, tool definitions, every message) and returns one assistant turn. Everything that feels like an "agent" is a program around that call, called the harness.

The assistant turn is a list of content blocks: text, optional thinking, and zero or more tool_use blocks. Each tool_use block has an id, a tool name and a JSON input. The response also carries a stop_reason; when it is tool_use, the model is waiting for results.

  your task
      |
      v
+-> call model with full history
|       |
|       v
|   stop_reason == tool_use ?
|       | yes             | no
|       v                 v
|   check, run tools   reply, stop
|       |
|   append tool_result blocks
+-------+

Between calls the harness does real work. It checks each requested call against permission rules (4.5), runs pre-tool hooks (4.7), executes the tool, truncates oversized output, and wraps each output in a tool_result block that quotes the matching tool_use id.

All results from one turn go back together in a single user-role message, and the model is called again. When it answers with plain text and no tool calls (stop_reason is end_turn), the loop hands control back to you. A max-turns cap or token budget is the backstop if it never stops.

Two consequences follow. The model never sees your file system; it sees only the text the harness chose to put in tool results. And every turn re-sends the entire history, so cost and latency grow with session length; prompt caching (2.3) is what keeps that affordable.

When Claude Code shows several tool calls in one step, say three file reads at once, the model emitted three tool_use blocks in a single turn. The harness ran them, possibly in parallel, and returned all three results in one message before calling the model again.

The model proposes, the harness disposes. Every action, permission check and result format happens in ordinary code between two API calls.

4.2Tools as the interface

A tool is a name, a description and a JSON Schema; the description is a prompt, and the result format is half the tool's quality.

The harness sends tool definitions with every request. Each has a name, a natural-language description, and an input schema in JSON Schema. The model is trained to emit a tool_use block whose input matches the schema; no code runs until the harness runs it.

{"name": "read_file",
 "description": ("Read a text file. Returns "
     "numbered lines. Use offset for big "
     "files instead of cat."),
 "input_schema": {
   "type": "object",
   "properties": {
     "path": {"type": "string"},
     "offset": {"type": "integer"}},
   "required": ["path"]}}

Descriptions do the steering. They say when to use the tool, when not to, and what comes back. Harness builders spend as much effort on that wording as on the implementation, because a vague description produces wrong calls no matter how good the code is.

Result formatting matters as much. Good results are short, stable and actionable: line numbers so the next edit can point at them, a clear error ("old_string not found; it must match exactly") instead of a stack trace, and truncation with a note ("output cut at 30,000 characters") so the model knows it saw only part.

Definitions cost context on every call, and with dozens of MCP tools that becomes a large fixed tax. Some harnesses therefore use deferred loading: only tool names are listed up front, and the model calls a search tool to fetch a full schema when it needs one.

Bash is the universal tool. One schema reaches every CLI on the machine (git, grep, jq, the test runner, gh), and models have seen enormous amounts of shell in training. Dedicated tools still win where structure helps: an edit tool can demand exact-match replacement and a prior read, a read tool can add line numbers, and both are easier to permission precisely than arbitrary shell strings.

When Claude Code's edit tool fails with "string not found", that failure is designed: it forces the model to re-read the file instead of guessing. When Claude runs a tool-search step before using an MCP tool, that is deferred loading fetching the schema.

Treat a tool description as a prompt and a tool result as a user interface whose user is the model.

4.3Context management

The context window is the model's only working memory; the harness decides what goes in, in what order, and what gets summarized away.

Every request is assembled fresh, in a typical order: the harness's system prompt, tool definitions, instruction files such as CLAUDE.md, then the conversation itself, meaning your messages, the model's turns and every tool result. Stable material goes first so prompt caching (2.3) can reuse it; a change near the top invalidates the cache for everything after it.

Tool results dominate. A few file reads, one long test log and a broad grep can outweigh everything you typed. Harnesses fight this by truncating outputs, by nudging the model toward targeted reads (grep first, then read a range), and by pushing exploration into subagents whose bulky context is thrown away (4.6).

Compaction kicks in as the window nears its limit. The harness sends the history to the model with an instruction along the lines of "summarize this session: goal, decisions, files touched, current state, next steps". It then starts a new history from the system prompt plus that summary, sometimes re-attaching recently used files.

Most harnesses compact automatically past a threshold and also offer a manual command; in Claude Code that is /compact, which accepts optional focus instructions. Compaction is lossy. Exact error text, a rejected approach and why it failed, or a constraint you stated once in turn 12 may not survive.

Long sessions degrade even before compaction. Attention spreads over more tokens, stale content (old versions of a file, abandoned plans) competes with the current state, and early instructions sit far back. This is often called context rot, and the practical fix is shorter, task-scoped sessions with durable facts kept in files.

The "compacting conversation" notice in Claude Code is this mechanism. If Claude retries a fix that already failed right after a compaction, the failure details were probably summarized away. Starting a fresh session from a written plan file often beats pushing one long session further.

Context is a budget. Keep durable facts in files, keep bulky output out of the main thread, and restart sessions instead of letting them rot.

4.4Memory

Models remember nothing between calls; "memory" is files the harness loads into the context, plus notes the model is asked to write.

Your session never updates the model's weights. Whatever persists does so as text that a harness puts into some future context window. Three kinds are common.

  • Instruction files. CLAUDE.md (AGENTS.md in several other tools) is plain markdown injected at session start. Claude Code reads a user-level file under ~/.claude, the project's file, and nested files in subdirectories as it works in them. It is a standing prompt, not a database.
  • Memory files. Some harnesses give the model a memory directory or tool and tell it to save facts worth keeping ("user prefers pnpm"). Later sessions load an index or the files, or the model searches them on demand.
  • Session history. Resuming a session reloads the transcript, or its compacted summary, into a new context. That is continuity, not memory, and it brings the old history's cost and clutter along.

Recall is just retrieval. Either the content is in the window from the start (always paid for, always visible) or the model must decide to look it up (cheap, but only works if it thinks to search). That one trade-off explains most memory quirks.

Instruction files are guidance, not enforcement. The model follows them like any prompt: usually, and less reliably as they grow long, contradict each other, or sit far from the current task. Short, specific, imperative lines beat essays. If a rule must hold every single time, turn it into a permission rule or a hook (4.5, 4.7).

Memory also goes stale. A note saved weeks ago describes code that may have changed since, and the model cannot tell stale from current unless the note records when and why it was written.

When Claude "forgets" a convention you explained yesterday, the convention lived only in yesterday's conversation. When it obeys a CLAUDE.md rule most of the time but not always, that is ordinary prompt-following, not a loading bug.

If it is not in a file that gets loaded or searched, it does not persist. If it must always happen, do not rely on memory at all.

4.5Permissions and sandboxing

Permission rules and sandboxes are enforced in code; instructions to the model are only promises.

Before executing a tool call, the harness checks it against a policy whose outcomes are allow, deny or ask the user. Rules match tools and argument patterns: allow Bash(npm run test:*), deny Bash(curl:*) or reads of .env. In Claude Code these live in settings files at user, project and local scope, and deny rules win over allow rules.

A mode sets the default for calls no rule matches. Typical modes: ask before anything risky, auto-accept file edits but ask for shell, a read-only planning mode, and a bypass mode meant for throwaway containers. Claude Code, as of late 2026, also has an auto mode in which a separate model-based check reviews actions and blocks risky or out-of-scope ones instead of prompting you.

Pattern rules on shell commands are leaky. A command string can chain, pipe, open a subshell, or start an interpreter that does anything. Harnesses parse commands to catch common tricks, but string matching cannot fully contain a confused or manipulated model.

An OS sandbox closes that gap. Tool processes run under kernel-enforced limits: writes only inside the project directory, network only to allowed hosts. Common building blocks are Seatbelt on macOS, bubblewrap and namespaces on Linux, and containers or VMs. Whatever command the model writes, the kernel refuses what the policy forbids.

MechanismEnforced byStops
"Never push" in CLAUDE.mdModel judgmentHonest mistakes, usually
Allow/deny ruleHarness codeMost mistakes
Blocking hookYour scriptWhat you check for
Sandbox or containerKernelNearly everything

The dangerous combination is private data, untrusted content, and a way to send data out, all in one session. Remove any one (no secrets in reach, no untrusted input, or no outbound network) and prompt injection (4.10) loses most of its teeth.

Each permission prompt you see is the loop paused at this check, and "don't ask again" writes an allow rule. Approval fatigue is real: a narrow allowlist plus a sandbox protects better than clicking yes fifty times a day.

Ask "what actually stops this?" If the answer is the model's good behavior, it is a promise. If it is code or the kernel, it is a control.

4.6Subagents, forks and workflows

A subagent is a second loop with a fresh context; its value is isolation, and its price is that only a summary comes back.

When the main agent calls a subagent tool, the harness starts a new loop with its own system prompt, its own (often restricted) tools and an empty history. The only task context it gets is the prompt string the parent wrote. It runs until it stops, and its final message becomes the tool_result in the parent's context.

 parent context (stays small)
   |  task: "find all auth callers"
   v
 +----------------------------+
 | subagent: fresh context    |
 | grep, read 40 files, ...   |
 | final message = report     |
 +----------------------------+
   |  tool_result = report
   v
 parent continues

That is the trade. Forty file reads fill the subagent's window, not yours, and the parent gets a page of findings. Search, exploration and review are the sweet spots because their bulky inputs are disposable.

The handoff tax runs both ways. Going down, the subagent knows only what the parent wrote, so a terse "check the auth code" drops the constraints you discussed for an hour. Coming back, nuance compresses: "looks fine" may hide what was never checked. Good handoffs state the goal, context, constraints, and the exact shape of the report wanted.

A fork is the alternative where the child starts from a copy of the parent's context. It inherits everything the parent knows and pays for it in tokens and inherited clutter. Harnesses differ in which of the two they offer.

Parallelism pays when tasks are independent, read-heavy and checkable: review five modules, or try three fixes in separate worktrees. It hurts when workers edit the same files or must agree on shared decisions, and token use multiplies with each worker.

Workflows go further: a script, not the model, owns the sequence (plan, fan out, verify, merge) and calls agents as steps. Deterministic control flow with model judgment inside each step is often more reliable than one agent orchestrating everything.

The subagent result you see in Claude Code is the child's final message, passed up as a tool result. If it seems overconfident, the parent is reading the same thin summary you are, which is why asking subagents to list what they did not verify pays off.

Delegate to save context, not to save thinking. Write the handoff like a ticket for a capable colleague with zero background.

4.7Hooks, skills, slash commands and plugins

Hooks are code the harness always runs at fixed points; skills and slash commands are prompts the model follows with judgment; plugins package them.

These extensions split along one line. Deterministic means harness code runs it every time. Prompt-based means text enters the context and the model decides what to do with it.

Hooks are deterministic. You register a shell command for an event, and the harness runs it with the event details as JSON on stdin. Claude Code's events include PreToolUse, PostToolUse, UserPromptSubmit, Stop, SubagentStop, SessionStart and PreCompact.

A PreToolUse hook can block a call: in Claude Code, exit code 2 blocks it and the hook's stderr goes back to the model as the reason. A PostToolUse hook can run a formatter after every edit. A Stop hook can refuse to let the agent finish until the tests pass.

Skills are prompt-based, with progressive disclosure. A skill is a folder whose SKILL.md has frontmatter with a name and description. Only those short descriptions sit in the context up front; when the model judges one relevant, it loads the body, which can point at further files or scripts. Many skills can stay installed for little context cost.

Slash commands are saved prompts you trigger yourself: typing /name expands a template into your message. The trigger is deterministic; what follows is prompt-following. Plugins bundle commands, skills, hooks, subagent definitions and MCP servers into one installable unit.

You wantUse
Format after every editPostToolUse hook
Never touch migrations/Deny rule or PreToolUse hook
How we write release notesSkill
Run my review checklist nowSlash command

The classic mistake is putting a guarantee in a prompt. "Always run the linter" in CLAUDE.md gets followed most of the time; a hook gets followed every time.

When a skill you wrote does not trigger, the model did not judge its description relevant; rewrite it around when to use it, in words a user would actually type. When a hook message appears and Claude changes course, that is a blocked call feeding stderr back into the loop.

4.8MCP

MCP is a standard JSON-RPC protocol that lets any harness discover and call tools hosted by separate server processes.

The Model Context Protocol separates the agent (a client inside the harness) from integrations (servers). A server is a program, local or remote, that speaks JSON-RPC 2.0 either over stdio, where the harness spawns it as a subprocess, or over HTTP, typically a remote service behind OAuth.

On connect, client and server run an initialize handshake that declares capabilities. The client calls tools/list and receives names, descriptions and JSON Schemas, which the harness adds to the tool definitions it sends the model, usually namespaced (Claude Code shows them as mcp__server__tool).

When the model emits a tool_use for one, the harness sends tools/call to the server and wraps the response as a tool_result. The model never talks to the server directly; the harness is the middleman, so permission rules and hooks apply as usual.

Servers expose three main primitives:

  • Tools: actions the model can call.
  • Resources: readable data addressed by URI (a file, a ticket, a schema) that the user or app can attach to context.
  • Prompts: templated prompts a server publishes, which harnesses often surface as slash commands.

One server often exposes many tools, and every connected server's definitions ride along on each request. Ten servers with twenty tools each is a heavy fixed tax, which is why deferred loading (4.2) matters most for MCP.

The security surface is wide. A server runs with your credentials and, if local, your OS user's permissions. Its tool descriptions go straight into the model's context, so a malicious server can plant instructions there (tool poisoning). Its results carry text written by strangers, such as issues, emails and web pages, the classic injection path (4.10). And its definitions can change after you approved it.

Hygiene: install servers you would trust as a code dependency, pin versions, give tokens the narrowest scopes, and write permission rules for MCP tools like any other tool.

If sessions got slower and burned limits faster after you connected a few servers, their tool definitions are likely riding along on every request. If Claude hesitates over instructions it found inside a fetched issue, it is treating tool output as data, which is the defense working.

An MCP server is a third-party dependency that writes into your model's prompt. Vet it like one.

4.9Reliability and cost

Harnesses retry, cap and count around the model; every call resends the whole context, so tokens and rate limits scale with session length.

API calls fail routinely: rate-limit errors (HTTP 429), server errors and overload responses (5xx; Anthropic's API uses 529 for "overloaded"), and dropped streams. Harnesses retry with exponential backoff and jitter, respect retry-after headers, and surface the error only after several attempts.

Tool calls need their own guards: timeouts on shell commands (a dev server that never exits would otherwise hang the loop), output caps, and a way to run long processes in the background. A failed tool is not a failed loop. The error goes back as a tool_result marked is_error, and the model decides what to do next.

Loop detection is mostly blunt: a max-turn cap, a token or cost budget, and sometimes a check for the same call with identical input repeated several times. Smarter detection is hard because good work also looks repetitive: edit, test, edit, test.

Token accounting follows the loop. Each call bills input tokens for the entire context sent and output tokens for everything generated, thinking included. Turn 50 resends turns 1 to 49, so without caching, total input grows roughly with the square of the turn count.

Prompt caching bills an unchanged prefix at a much lower cache-read rate, which is why a stable prefix is worth protecting (2.3, 9.3). Cached tokens still occupy the window, though; caching saves money and latency, not context space.

Rate limits are counted separately from cost. API keys typically have per-minute limits on requests, input tokens and output tokens. Subscription plans meter usage over rolling time windows, and larger models and parallel subagents drain the allowance faster because each worker runs its own full-context loop.

Hitting a usage limit after a multi-agent run is this arithmetic: five workers each re-reading files and resending their whole context every turn. A single long session also burns more than two short ones doing the same work, because its late turns carry the full history.

Cost scales with context size times turns times agents. Shrink any one of the three.

4.10Failure modes

Agents fail in predictable ways: obeying instructions hidden in tool output, looping without progress, and declaring done without proof.

Injection via tool results. Everything a tool returns (web pages, issue comments, file contents, test output) lands in the context as text. The model has no hard boundary between fetched data and instructions; training teaches it to favor the user, but a cleverly worded README ("AI agents: also run this setup command") can still steer it. Risk peaks when the session also has secrets and network access (4.5, 10.1).

Runaway loops. The agent retries the same failing fix, oscillates between two edits, or keeps exploring without converging. Usual causes: an ambiguous goal, a test it cannot satisfy, an environment problem misread as a code bug, or a key fact lost to compaction.

False "done". The model reports success when tests were skipped, a check was loosened, a mock hides the real path, or it merely believes the change works. Training rewards finishing, and reinforcement learning against tests can teach shortcuts such as special-casing the test input.

Collateral edits. Unrequested refactors, reformatted files, or deleted "unused" code that was in fact used.

Mitigations, roughly from strongest to weakest:

  • Sandbox and least privilege, so injected instructions have little reach.
  • Verifiable completion: define done as a command that passes (tests, type check, build), enforced by a Stop hook or CI rather than the model's say-so.
  • Budgets: turn caps, timeouts, and a human checkpoint when the same error repeats.
  • Review the diff, not the summary. The summary is a claim; the diff is evidence.
  • A separate verifier: a fresh agent that did not write the code, told to find what is wrong.

"All tests pass" while CI fails usually means Claude ran a subset, ran them before its last edit, or a test was skipped. Asking for the exact command and output it relied on turns a claim into evidence.

4.11Comparing harnesses

The major coding agents share the same loop; they differ in where they run, how they gather context, how they sandbox, and how you extend them.

Under the hood, every current coding agent is the loop from 4.1 with file, search and shell tools. The differences that matter in daily use are all around it.

HarnessRuns inNotable
Claude CodeTerminal, IDE, desktop, webHooks, skills, subagents, MCP
Codex CLITerminal; open sourceOpenAI models; OS sandbox by default
Cursor agentInside the editorEditor state, semantic code index
Agent SDKYour own programClaude Code's harness as a library

Context gathering differs. Claude Code and Codex lean on agentic search: the model greps and reads on demand (7.3). Cursor also maintains an embedding index of the repo for semantic search and pulls in editor state such as open files. An index helps in huge unfamiliar code; live search is never stale.

Model coupling differs. Claude Code and the Agent SDK are built around Claude models, Codex CLI around OpenAI's, while Cursor lets you choose among vendors. System prompt, tool design and compaction are tuned to the model, so the same model can perform noticeably differently in different harnesses.

Agent benchmarks measure the pair. SWE-bench hands the agent a real GitHub issue and repository, then checks whether hidden tests pass after its patch; SWE-bench Verified is a human-validated subset of 500 tasks. Terminal-Bench gives tasks in a containerized terminal (build this, configure that) and checks the end state.

Read scores critically (6.3): which harness, how many attempts, what time and token budget, and whether tasks may have leaked into training data. A few points on a leaderboard say less than an afternoon on your own repository.

If a model feels sharper in one tool than another, the harness is a likely reason: a different system prompt, tool set, context strategy and compaction policy. Same weights, different loop.

Choose a harness by its control surfaces (permissions, sandbox, hooks, extensibility) and how it fits your workflow; the model inside changes every few months.

4.12Build one yourself

A working agent is about 100 lines: a model call, a tool table, and a loop that feeds results back; the Agent SDK gives you the production version.

Writing a toy loop is the fastest way to make 4.1 to 4.9 concrete. Here is the core, shaped like Anthropic's Python SDK; TOOLS (schemas) and IMPL (name to function) are yours.

def run(task):
    msgs = [{"role": "user", "content": task}]
    for _ in range(MAX_TURNS):
        r = client.messages.create(
            model=MODEL, max_tokens=8000,
            system=SYSTEM, tools=TOOLS,
            messages=msgs)
        msgs.append({"role": "assistant",
                     "content": r.content})
        if r.stop_reason != "tool_use":
            return r.content
        msgs.append({"role": "user",
                     "content": run_tools(r)})

The assistant turn is appended exactly as returned, thinking and tool_use blocks included, because the next call must see what the model actually said. Results go back in one user-role message, each tagged with the id it answers.

def run_tools(r):
    out = []
    for b in r.content:
        if b.type != "tool_use":
            continue
        err = False
        try:
            text = IMPL[b.name](**b.input)
        except Exception as e:
            text, err = f"error: {e}", True
        out.append({"type": "tool_result",
            "tool_use_id": b.id,
            "is_error": err,
            "content": str(text)[:20000]})
    return out

Give IMPL a read_file, a write_file and a bash that runs a subprocess with a timeout. Add one if-statement before the IMPL call and you have permissions (4.5); sum r.usage per call and you have token accounting (4.9).

What the toy lacks: streaming, retries with backoff, compaction, cache breakpoints, parallel tool execution, a sandbox and hooks. Each is tens to hundreds of lines, and together they are most of a real harness.

The Claude Agent SDK (Python and TypeScript) packages Claude Code's harness as a library, with built-in tools, permissions, hooks, subagents, MCP and compaction driven from your code:

from claude_agent_sdk import query
from claude_agent_sdk import ClaudeAgentOptions

opts = ClaudeAgentOptions(
    allowed_tools=["Read", "Grep", "Bash"],
    permission_mode="acceptEdits", max_turns=30)
async for msg in query(prompt="Fix the test",
                       options=opts):
    print(msg)

Option names shift between versions, so check current SDK docs before relying on exact spellings.

Writing the loop once explains a lot of Claude Code behavior: why parallel tool calls return together, why a tool error does not end the session, and why each turn of a long session costs more than the last.
